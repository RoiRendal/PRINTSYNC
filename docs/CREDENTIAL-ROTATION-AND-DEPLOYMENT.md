# Credential rotation, and preparing for the first deployment

**Audience:** the project manager (no programming required) and the development team.

**Why this document exists.** Two items have been carried as release blockers since
Tier 3 and are the only things standing between PRINTSYNC and a safe test run:

1. The three development accounts use predictable, guessable passwords that were
   written down during early development.
2. The Supabase **service-role key** — the master key to the entire database — lives in
   a file called `backend/.env`.

Both are quick to fix. This document gives the exact steps, the reason for each, and a
way to confirm each one worked. **Do the steps in order: rotate the passwords first,
then the key.** The key step depends on the passwords being changed, not the reverse.

---

## Part 0 — What is actually at risk

| | What it is | What an attacker gets | Where it lives now |
| --- | --- | --- | --- |
| **The three accounts** | Logins for the manager and two staff members | Everything those accounts can do: ring up sales, change stock, delete customers | Passwords are known and guessable |
| **The service-role key** | A single string that lets its holder read and write **every table, bypassing every permission check** | The entire database. Not "some data" — all of it, plus the ability to delete it | `backend/.env`, a plain text file |

They compound. A known password gets someone into the system; the key gets them
everything the system is built on. On a URL reachable from the internet, the key is
the higher-value target of the two — which is why it is second only in *order*, not in
importance.

**A note on what "the key" is.** Supabase has two generations of API keys:

- **Legacy** keys are long strings beginning `eyJ` (`anon`, `service_role`).
- **New** keys are short strings: `sb_publishable_…` (low privilege, safe for browsers)
  and `sb_secret_…` (high privilege — this is the one we care about).

This project is already on the **new** key system, which is good news: a secret key can
be created and revoked independently, without disturbing anything else. Legacy keys
cannot be rotated at all any more — Supabase has retired that ability — so a project
still on them has to migrate first. **Not our problem. We are on the good path.**

## Part 1 — Rotate the three account passwords

### The easy, reliable way: the project's own tool

The repository ships a provisioning script that creates or repairs an account, and it
has a switch specifically for replacing an existing password. This is better than
clicking around the Supabase dashboard because it does three things at once: sets the
password, keeps the user's profile and role intact, and writes an audit-log entry
recording that it happened.

Open a terminal in the `backend` folder and run this **once per account**, changing the
two values marked `<< >>`. The password must be at least 8 characters.

**PowerShell:**

```powershell
cd backend

$env:PROVISION_EMAIL           = 'admin@printsync.com'
$env:PROVISION_PASSWORD        = '<<new password>>'
$env:PROVISION_NAME            = 'Admin'
$env:PROVISION_POSITION        = 'System Administrator'
$env:PROVISION_ROLE            = 'admin'
$env:PROVISION_RESET_PASSWORD  = 'true'
npm run provision:user
```

**macOS / Linux:**

```bash
cd backend

PROVISION_EMAIL=admin@printsync.com \
PROVISION_PASSWORD='<<new password>>' \
PROVISION_NAME='Admin' \
PROVISION_POSITION='System Administrator' \
PROVISION_ROLE=admin \
PROVISION_RESET_PASSWORD=true \
npm run provision:user
```

Repeat for the other two, changing only the four marked lines:

| Email | `PROVISION_NAME` | `PROVISION_POSITION` | `PROVISION_ROLE` |
| --- | --- | --- | --- |
| `noah@printsync.com` | `Noah` | `Press Operator` | `staff` |
| `mika@printsync.com` | `Mika` | `Press Operator` | `staff` |

`PROVISION_RESET_PASSWORD=true` is the part that matters. Without it the script
deliberately preserves the existing password and prints a line telling you so — it will
look like it worked while changing nothing.

### What a good replacement password looks like

- **At least 12 characters.** Length beats complexity: `teal-bucket-harbour-42` is far
  stronger than `P@ssw0rd!` and much easier to type on a shop-floor keyboard.
- **Different for each account.** If one leaks, the others survive.
- **Not reused from anywhere else.** Not the Wi-Fi, not a personal account.
- Generated by a password manager, or four unrelated words joined by dashes.

Do **not** write them in the repository. `0_never-push-this-dump-folder/` is gitignored
and is the right place for the local record, but it must stay local.

### Verify it worked

1. Start the API (`cd backend && npm run dev`) and the app (`cd frontend && npm run dev`).
2. Sign in at <http://localhost:3000> with the **new** password. It must succeed.
3. Sign out, and try the **old** password. It must fail.
4. Check the audit log in the app — there should be a `user.provisioned` entry for each
   account, with today's date.

### One caveat worth knowing

Changing a password does **not** instantly sign out anyone already holding a session.
Supabase sessions are tokens, and an already-issued access token stays valid until it
expires. In PRINTSYNC that is **one hour**; the refresh token lives **30 days**.

For a test run this is fine — the only people with sessions are the people whose
passwords you are changing. If you ever need a hard cutoff, delete and re-create the
account rather than just changing its password.

## Part 2 — Move the master key out of `backend/.env`

### First, the trap that makes this step necessary

The backend reads its configuration in a way that gives **`backend/.env` priority over
the hosting platform's environment variables**. In `backend/src/config/env.ts`:

```ts
dotenv.config({ override: true });
```

`override: true` means: if a value exists both in the file and in the real environment,
**the file wins**.

That single word is why this step is not optional. Picture the sequence:

1. You create a new key in Supabase.
2. You set it correctly in your hosting dashboard's environment variables.
3. You deploy. The old `backend/.env` ships along with the code.
4. The app ignores your new key, loads the **old** one, and either breaks or keeps
   running on a key you believed you had retired.

You would have done everything right and still be using the compromised key. So the goal
is not just "put the key somewhere better" — it is **"make sure the file is not there
competing with it."**

### Step 1 — Create a new secret key

1. Open the Supabase dashboard for the project.
2. Go to **Project Settings → API Keys**.
   (There is no separate "Settings → API" page any more — everything lives here.)
3. Create a **new secret key**. Give it a name that says what uses it, for example
   `printsync-api-production`.
4. Copy the value. It begins `sb_secret_`. **It is shown once.** If you lose it, create
   another — there is no "reveal" later.

> Supabase recommends a separate secret key for each backend component, so that leaking
> one only forces you to rotate that one. We have one component, so one key is right.

**Do not delete the old key yet.** Deleting is irreversible and you have not switched
over. That is the next step.

### Step 2 — Put the new key where the server will find it

**Locally**, edit `backend/.env` and replace the `SUPABASE_SERVICE_ROLE_KEY` value with
the new one. Nothing else in that file changes.

**On the hosting platform**, add it as an environment variable with exactly this name:

```
SUPABASE_SERVICE_ROLE_KEY
```

Most platforms have a section called **Environment**, **Environment Variables**, or
**Config Vars** in the service's settings. Add these five, taking the values from your
local `backend/.env`:

| Variable | Value |
| --- | --- |
| `SUPABASE_URL` | Your project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | The **new** `sb_secret_…` key |
| `FRONTEND_ORIGIN` | The exact URL the app will be opened at, e.g. `https://printsync.example.com` |
| `NODE_ENV` | `production` |
| `PORT` | Leave unset — most platforms inject their own |

**Then make sure `backend/.env` does not exist on the server.** The repository already
ignores it (`.gitignore` has `**/.env`), so a normal git-based deploy will not include
it. Confirm it anyway, because a deploy that copies a folder rather than cloning a
repository will take it along. If the file is present and holds the old key, the
rotation has not happened as far as the running server is concerned.

`FRONTEND_ORIGIN` is not cosmetic. The API allows exactly **one** origin, not a
wildcard. If it does not match the address in the browser's address bar exactly —
including `https://` and excluding any trailing slash — every request is refused by the
browser and the app appears completely broken.

### Step 3 — Confirm the new key works, *then* delete the old one

1. Deploy, or restart the API locally, with the new key in place.
2. Sign in and open a page that reads real data — the inventory list is a good choice.
   If it loads, the key is working.
3. Now go back to **Project Settings → API Keys** and delete the old secret key.

Deleting a secret key **cannot be undone**. Deleting it before step 2 is verified locks
you out until you create another one.

### If the old key was ever exposed

Rotating it is only half the job. Also check:

- Was it ever committed to git? Search the history, not just the current files.
- Was it pasted into a chat, a ticket, a screenshot, or a document?
- Does anyone outside the team have a copy — including a contractor's machine?

The key grants unrestricted database access. If it was exposed, assume the data was
readable and treat any change to the data since then as suspect.

## Part 3 — Before the test run

The two security steps above are necessary but not sufficient. Deployment also needs
configuration the repository does not yet contain, and there is one decision to make
first.

### The decision: one address, or two?

PRINTSYNC logs users in with a **cookie**, and that cookie is currently set to
`SameSite=Lax` (in `backend/src/shared/authCookies.ts`). In plain terms, a `Lax` cookie
is only sent back to a site that is the *same site* as the one that set it.

The catch is what "same site" means. Browsers use the **public suffix list** to decide,
and almost every free hosting platform puts its default domain on that list. We checked
it directly rather than assuming:

| Hosting platform's default domain | On the public suffix list? |
| --- | --- |
| `*.vercel.app` | Yes |
| `*.onrender.com` | Yes |
| `*.netlify.app` | Yes |
| `*.up.railway.app` | Yes |
| `*.fly.dev` | Yes |
| `*.herokuapp.com` | Yes |
| `*.web.app`, `*.pages.dev`, `*.azurewebsites.net` | Yes |

"On the list" means every `something.platform.com` is treated as its **own** site. So:

| Where the app and API live | Does login work? |
| --- | --- |
| Same address — the API serving the app | ✅ Yes |
| `app.example.com` + `api.example.com`, a domain you own | ✅ Yes |
| `printsync.vercel.app` + `printsync-api.vercel.app` | ❌ **No** |
| `frontend.onrender.com` + `backend.onrender.com` | ❌ **No** |
| `printsync.netlify.app` + `printsync.fly.dev` | ❌ **No** |

The bottom three rows are the trap, and they are the *default* outcome of the obvious
approach — deploy the frontend to one service, the API to another. Login will appear to
succeed and then immediately behave as if the user is signed out, and the live-update
stream will fail as well. It looks like a broken application rather than a configuration
mistake, and it is the kind of thing that costs an afternoon to diagnose.

**Recommendation: serve the app and the API from one address.** The backend serves the
built frontend as static files, so there is one deployment, one URL, no CORS to
configure, and the cookie problem cannot arise. It is also the cheapest, and the easiest
to tear down after the test run.

Two separate deployments are still possible, but one of these has to be true:

- **You own a domain** and put the app and API on subdomains of it
  (`app.yourdomain.com` + `api.yourdomain.com`). Requires a domain and HTTPS.
- **The cookie is changed to `SameSite=None; Secure`** in
  `backend/src/shared/authCookies.ts`. This is a code change, only works over HTTPS, and
  relaxes a deliberate security setting — so it should be a considered decision, not a
  workaround.

### What the deployment must provide

1. **A build that respects the workspace order.** The backend imports shared contracts
   from `packages/shared-types`, and it reads the **compiled** output. So that package
   must be built *before* the backend is type-checked or built. A platform that builds
   `backend/` in isolation will fail. Either a Dockerfile built from the repository root,
   or a documented three-step build command, is required.
2. **`FRONTEND_ORIGIN` set to the exact public URL** of the app.
3. **`NODE_ENV=production`**, so the session cookie gets its `Secure` flag. Without it,
   the cookie is sent over plain HTTP and the browser may reject it on HTTPS.
4. **A reverse proxy that does not buffer `GET /events`.** The route already sends
   `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`; a proxy that
   ignores them holds the stream and the interface looks frozen with no error. The
   25-second heartbeat is chosen to sit under nginx's 60-second default.
5. **Exactly one API instance.** The live-update bus is in-process, so a second instance
   serves changes it never hears about. Scaling up comes later and needs a code change.
6. **Do not ship `backend/.env`, `0_never-push-this-dump-folder/`, or `node_modules`.**
   The dump folder contains the database schema and the old passwords.

### What a test run does *not* need

- A custom domain. Subdomains of one platform domain are fine.
- A paid tier, for a two-or-three-person trial.
- The `LISTEN`/`NOTIFY` work, analytics caching, or branch protection. Those are
  capacity and process improvements, not launch requirements.

## Part 4 — Checklist

Work down the list; each line is verifiable without reading code.

**Passwords**

- [ ] All three accounts signed in successfully with a new password
- [ ] All three old passwords rejected
- [ ] Three `user.provisioned` entries in the audit log, dated today
- [ ] New passwords recorded somewhere private, not in the repository
- [ ] Nobody else has a copy of the old ones

**Master key**

- [ ] A new `sb_secret_…` key exists, named for what uses it
- [ ] `backend/.env` locally holds the new key
- [ ] The hosting platform holds the new key as `SUPABASE_SERVICE_ROLE_KEY`
- [ ] **`backend/.env` does not exist on the server**
- [ ] The deployed app loads real data (inventory list renders)
- [ ] The old secret key has been **deleted** from the Supabase dashboard
- [ ] The old key is not in git history, a chat, a screenshot, or a document

**Deployment**

- [ ] App and API are reachable at **one** address
- [ ] `FRONTEND_ORIGIN` matches that address exactly
- [ ] `NODE_ENV=production` is set
- [ ] Signing in works, and survives a page refresh
- [ ] The connection indicator reads **Live**
- [ ] A change made in one browser appears in a second browser within ~1 second
- [ ] A checkout completes, and the receipt prints the sale
- [ ] The proxy is not buffering `GET /events`

## Appendix — When something goes wrong

| Symptom | Most likely cause |
| --- | --- |
| Login succeeds, then the app behaves as if signed out | App and API are on different sites, so the `Lax` cookie is not sent. Put them on one address. |
| Every request blocked, browser console mentions CORS | `FRONTEND_ORIGIN` does not match the address bar exactly. Check `https://`, the subdomain, and no trailing slash. |
| Connection indicator never reaches "Live", but the app works | The proxy is buffering `GET /events`. The app falls back to polling, so it degrades quietly rather than failing. |
| "Supabase has not been configured for this environment" | `SUPABASE_URL` or `SUPABASE_SERVICE_ROLE_KEY` missing **on the server** — or a stale `backend/.env` is overriding them. |
| The provisioning script says the password was preserved | `PROVISION_RESET_PASSWORD=true` was not set. |
| Data appears stale to some users but not others | More than one API instance is running. |
